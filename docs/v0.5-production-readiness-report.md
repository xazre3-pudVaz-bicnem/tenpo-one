# v0.5.0 PRODUCTION READINESS 完了報告

新業務機能を追加せず、既存機能を「本番で壊れない・漏れない・遅くならない」状態へ引き上げた。
セキュリティ・障害耐性・大量データ耐性・バックアップ/復旧・運用監視・データ保護・リリース安全性・
UX最終巡回の8テーマを、監査 → 修正 → 自動テストの順で実施した。

---

## 1. セキュリティ

商用マルチテナントSaaSとして全体監査し、**3つのCRITICALを含む脆弱性を修正**した。

### CRITICAL（DB層・migration 00031）
- **C1 自己スーパー管理者昇格**: 任意の認証ユーザーが `PATCH /profiles {is_cypress_admin:true}` で
  全テナントを侵害できた → BEFORE UPDATEトリガーで is_cypress_admin/status/pin_code のユーザー文脈変更を拒否。
- **C2 自己org_owner昇格**: store_manager が `PATCH /memberships {role:org_owner}` で組織乗っ取り →
  memberships書込RLSを org_owner/hq_admin のみに厳格化 + 自己role変更禁止トリガー。
- **M2 監査ログ汚染**: log_audit が p_org を検証せず任意orgへ記録 → メンバー資格を検証。

実データでC1（トリガー拒否）・C2（RLS 0行・role不変）を攻撃再現し封鎖を確認。

### アプリ層（IDOR 15件・権限昇格 3件ほか）
- **IDOR**: staff管理のprofileId未検証（他組織へのPIN設定・停止）、POS決済端末・予約ヘルパー・
  レジ開閉局・仕訳・在庫移動・クーポン・お知らせの店舗所属チェック欠落を修正。
- **role ceiling**: canAssignRole（role序列）で招待・role変更が caller ロールを超えないよう強制。
  店長のHQロール招待を封鎖。招待の平文パスワード廃止（サーバー生成）。
- **manager store-scope**: role変更・停止・PIN設定を担当店舗と交差する対象のみに制限。
- **PIN**: 平文保存廃止・scryptハッシュ化（既存カラム流用・後方互換で自動移行）+ 打刻ブルートフォース制限。
- **file_path**: documentsパスを organization_id プレフィックスで検証。
- **CSP**: default-src 'self' / base-uri 'none' / object-src 'none' / frame-ancestors 'self' 等を追加
  （本番enforce・開発Report-Only）。
- **feature flag強制**: order への BEFORE INSERT トリガーで、qr_order OFF企業のQR注文作成を拒否（migration 00032）。

### 確認済み（問題なし）
service role鍵はserver-only・NEXT_PUBLIC非露出。RLS生成は `%I`+ハードコード配列でSQLi不可。
Stripe webhookは署名+冪等。dangerouslySetInnerHTMLは静的JSON-LDのみ。

## 2. RLS / IDOR

4層防御（UI can() → Server Action requirePermission → SECURITY DEFINER RPC → RLS）。
createAdminClient全使用箇所で所有権チェックを確認・補修。
検証: verify-security.mjs 45チェック・security-idor.spec.ts 5・verify-flow の企業/店舗分離。

## 3. Rate Limit

lib/rate-limit.ts（interface・将来Redis差し替え可）。公開予約をserver action化しIP制限、
予約決済チェックアウト・状態照会（enumeration防止）、PIN打刻、アップロードに適用。QRはDB側5/min/table。
ログインはSupabase Auth側制限に依存（**BLOCKED**）。多インスタンスでin-memoryは不完全→本番Redis（**BLOCKED D**）。

## 4. Storage

documents（非公開・署名URL）/ menu-images（公開・商品画像専用）。パス第1階層=organization_idのRLSで
テナント境界を強制。アップロードはMIME/拡張子/サイズ/ファイル名/path traversalをサーバー検証。docs/storage-security.md。

## 5. Session

lib/auth.ts はリクエスト毎に profile.status / membership.status を再読込し停止即遮断。
**企業status（suspended/cancelled/pending_deletion）でのログイン遮断を追加**（cypress運営は除外）。

## 6. 障害耐性（docs/resilience.md）

Timeout（health 5秒）・error boundary（エラーID表示）・OfflineBanner・Realtime 30秒フォールバック。
**二重処理防止**: finalize_order（FOR UPDATE+status guard）・refund_order（超過拒否）・給与確定ロック・
仕訳source_id冪等・webhook冪等。副作用処理を無条件リトライしない。

## 7. Transaction

会計・返金・仕入入荷・在庫移動・給与確定・月次締め・予約確定はいずれも単一RPC（=1トランザクション）で
完結し、途中失敗で半端な状態を残さない。予約は advisory lock で二重予約防止。

## 8. Performance（docs/performance.md）

**N+1ゼロ**（監査確認・`.map(async)` 0件）。ダッシュボードのクエリ数は店舗数非依存（約40本固定）。
真の負荷は「期間×全店の行数をJS集計」→ 段階的にロールアップ/集約RPCへ。ベンチマーク下地
（scripts/benchmark・ローカル専用ガード）。既存規模で全クエリ500ms未満。

## 9. Index（migration 00030）

refunds(store_id,business_date)〔最優先〕・expenses複合・invoices・order_items・journal_lines・
pg_trgm GIN（customers/reservations検索のILIKE全件走査解消）。本番大量データはCONCURRENTLYで流す旨を明記。

## 10. Backup（docs/backup-restore.md）

対象（PostgreSQL/Storage/env/migration/Git/法定rule）と方式を整理。PITR前提。
RPO≤5分・RTO≤2時間（**目標値**・本番設定で確定）。確定データは物理削除禁止（トリガー）。

## 11. Restore

ローカル/テストDBでの復旧ドリル手順（migration→型生成→seed→verify-flow→audit-integrity）。
復元後は audit-data-integrity で整合性確認。

## 12. Monitoring（docs/observability.md）

エラーID（ERR-XXXXXX）でユーザー↔内部ログ↔system_errors を橋渡し。構造化ログ（PII/秘密値をsanitize）。
system_errors（監査ログと分離・CYPRESS閲覧・migration 00029）。/api/health拡張（app/db/auth/version/environment・
秘密値なし）。**/admin/system**（バージョン・migration・health・テナント/店舗/ユーザー数・最近のエラー）。
captureServerError/withErrorCapture を返金/締め/給与確定/仕訳へ適用。

## 13. Data Protection（docs/privacy-operations.md）

テナントoffboarding（active→suspended→cancelled→pending_deletion・物理削除しない・migration 00029）。
**顧客匿名化**（PII列除去+取引保持+anonymized_at+監査）。給与・銀行（下4桁）・住所・生年月日は権限厳格化。
法定保存期間は根拠なく決めず専門家確認へ分離（**BLOCKED E**）。

## 14. Release Safety（docs/migration-policy.md / release-strategy.md）

既存migration書き換え禁止・新規追加のみ。Expand/Contractパターン。破壊的変更は分割。
Rollback: アプリ=Vercel previous / DB=forward fix。feature flagで段階ロールアウト。
バージョンをhealth/System画面で確認。リリースチェックリスト完備。

## 15. UX（全端末巡回）

ux-sweep.spec.ts: 10 route × 5 viewport（1920/1366/iPad横縦/iPhone）でコンソールエラー0・横スクロール検出。
**発見・修正**: /app/reports が iPhone幅で横スクロール（期間フォームのw-36固定 + grid子のmin-width:auto）→
period-formのレスポンシブ化 + grid子への `min-w-0`（TableWrapのoverflow-x-autoが正しく機能）で解消。ux-sweep 50/50。
フォーム二重送信防止（送信中ボタン無効化）・危険操作の確認ダイアログ（返金/取消/締め/給与確定）。

## 16. Accessibility

キーボード操作・focus・aria・label・コントラストを既存UIキットで担保。危険操作は確認ダイアログ+理由入力。
体系的a11y監査は次段階の課題として記録。

## 20. 残Blocker（分類）

### A. コードで解決済み
上記すべて（セキュリティ・観測性・index・障害耐性・データ保護構造・UX修正）。

### B. Vercel/Supabase本番設定
PITR保持期間・Storageバックアップ設定確認 / 本番env・Supabase Auth URL・NEXT_PUBLIC_SITE_URL /
rate limit共有ストア（実体はD）。

### C. 実機
レシートプリンター・キャッシュドロア・Stripe Terminal。

### D. 外部サービス
Stripe本番決済/Billing・メール(Resend)・LINE・銀行API・freee/KOT・外部監視SaaS(Sentry等)・
rate limit用Redis(Upstash等)。

### E. 専門家確認
所得税・社会保険・割増率・年末調整の法定値（/admin/legal-rules/review 後に投入）・
個人情報/会計帳簿の法定保存期間・漏えい通知義務。

**コードだけで解決できるA項目の積み残しはない**。監査で見つかった穴はすべて修正済み。
残る性能スケール項目は「初期本番規模では不要・閾値到達時に着手」と docs/performance.md に整理。

## 21. 外部サービス開始前に必要なこと

1. 本番Supabaseのバックアップ/PITR設定確認（B）
2. rate limitを共有ストア（Redis/Upstash）へ差し替え（D・多店舗同時運用前に）
3. 外部監視（Sentry等）を lib/observability の差し替えポイントへ接続（D）
4. 専門家による法定値確認と投入（E）
5. 実機（プリンター/ドロア/Terminal）と決済・通知の外部サービス接続（C/D）
6. docs/release-strategy.md のチェックリストで本番リリース

## v0.5.0の到達点

- 他企業データを見られない（IDOR全面修正・RLS+トリガー）
- 権限昇格できない（C1/C2/C3封鎖）

- 復旧手順がある（disaster-recovery/incident-response）
- エラーを追跡できる（エラーID・system_errors・System画面）
- 個人情報の扱いが整理されている（匿名化・offboarding・棚卸）
- 安全にmigrationできる（Expand/Contract・forward fix）
- 全主要端末でUIが崩れない（ux-sweep 50ケース）
- 既存業務テストが全GREEN
