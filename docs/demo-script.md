# 商談デモ台本（TENPO ONE）

対象: 飲食店・小売の経営者/店長への商談デモ。5分/15分/30分の3パターン。
共通の核心メッセージ: **「予約・POS・顧客・利益が1つのデータで繋がっている」**。
機能を羅列するのではなく、上記メッセージが伝わる最短導線で見せる。

---

## 事前準備（共通）

- デモ環境URL・デモ企業（渋谷店）を用意
- ブラウザタブを事前に開いておく（切替のもたつきを無くす）
  1. タブA: 渋谷店長ログイン済み（`shibuya@demo.tenpo.one`） → ダッシュボード
  2. タブB: シークレットウィンドウで `/book/tenpoone-shibuya`（公開予約ページ、未入力状態）
- パスワードは全アカウント共通 `TenpoOne-Demo1!`（画面共有中は入力を速めに）
- 直前に一度リハーサルし、当日使う日時・卓・商品を決めておく（毎回同じ動線で迷わない）
- 客役の名前は「デモ 太郎」等、毎回変えて重複データを避ける

## パターンA: 5分版 — コア訴求のみ

**ゴール**: 「バラバラのExcel/紙/複数ツールで管理していたものが、1つに繋がる」を体感させる。
機能の広さより**繋がりの速さ**を見せる。

### 事前準備
- タブA（渋谷店長・ダッシュボード）、タブB（公開予約ページ）のみで足りる
- 事前に唐揚げ・生ビール等、単価のわかりやすい商品を1〜2品選んでおく

### 画面遷移手順

| 時間 | 操作 | 話すポイント |
|---|---|---|
| 0:00-0:30 | タブB: 公開予約ページで氏名・電話・人数・時間を入力し予約送信 | 「これは店舗のWebサイトに埋め込む予約ページです。お客様がスマホから直接予約できます」 |
| 0:30-1:30 | タブA: 予約台帳に切替 → 今送った予約がリアルタイムで表示 | 「今送った予約が、電話を受けることなくそのまま台帳に載ります。テーブルもおすすめ候補から選ぶだけです」→ テーブル割当 |
| 1:30-2:00 | ステータスを 来店 → 着席 に進める | 「来店・着席もワンタップです」 |
| 2:00-3:30 | 予約カードから「注文へ」→ POSで商品をタップ → 会計（現金/カード併用） | 「予約から直接POSに入り、会計まで同じ画面で完結します。分割会計や複数の支払い方法の併用もできます」 |
| 3:30-4:30 | 顧客管理へ切替 → 今の客の来店履歴・累計金額が即反映されているのを見せる | 「会計した瞬間に、顧客カルテの来店回数・累計金額が自動更新されます。これを手入力している店舗が本当に多いです」 |
| 4:30-5:00 | ダッシュボードへ切替 → 本日売上に反映されているのを見せる | 「経営者は、レジを締めなくても今この瞬間の売上が見えます。予約・接客・会計・顧客・経営、全部が同じデータです」 |

### 見せ場
- 予約送信からダッシュボード反映までの一連の流れを**画面遷移を止めずに**見せること（「裏で連携する」のではなく「同じデータを見ている」ことが伝わる）

### 想定質問と回答

| 質問 | 回答 |
|---|---|
| 今使っているPOSレジからデータ移行できるか | CSVインポート機能で商品・顧客・仕入先データの取込に対応。POSベンダー固有形式は個別確認が必要 |
| クレジットカード決済は実際にできるのか | Stripeとの決済基盤は実装済みで、テストモードで動作確認済み。実際の本番決済には契約者様のStripeアカウント設定が必要（基盤実装済み・接続待ち） |
| 複数店舗を経営しているが対応できるか | 対応。本社アカウントは全店舗を横断確認でき、店長アカウントは自店舗のみに制限される権限設計（後半の15分/30分デモで詳しく） |

## パターンB: 15分版 — +QRオーダー・レジ締め・本社ダッシュボード

**ゴール**: 5分版の核心に加え、**現場のオペレーション効率化**（QR注文・キッチン連携・レジ締め）と
**経営の見える化**（本社ダッシュボード）を見せる。

### 事前準備
- 5分版に加えて追加で開いておくタブ
  3. タブC: 店長画面のキッチン（KDS）画面（`/app/kitchen`）
  4. タブD: 本社アカウント（`hq@demo.tenpo.one`）でログイン済み・別ブラウザまたはシークレットウィンドウ
- レジが未開局なら事前に開局しておく（デモ中の開局操作は省略可）
- QRコード表示用にテーブル設定画面のURLをブックマークしておく

### 画面遷移手順

| 時間 | 操作 | 話すポイント |
|---|---|---|
| 0:00-5:00 | パターンAと同じ流れ（予約→台帳→POS→会計→顧客→ダッシュボード） | 同上 |
| 5:00-5:30 | 設定 → フロア・テーブル → QRコード表示 | 「テーブルに置くQRコードです。印刷してテーブルに置くだけで運用開始できます」 |
| 5:30-7:00 | スマホ幅のシークレットウィンドウでQR先URLを開き、メニューから注文 | 「お客様がスマホで直接メニューを見て注文できます。ログイン不要、売り切れは自動でグレーアウトします」 |
| 7:00-8:30 | タブC（キッチンKDS）に切替 → 今の注文が自動で表示される（更新操作なし） | 「厨房の画面には自動で注文が流れます。手動更新は不要です。ステーションごと（キッチン/ドリンク）に振り分けられ、経過時間で警告色が変わります」→ 調理開始→完成→提供済 を実演 |
| 8:30-10:30 | タブA: レジ・小口現金 → レジ締め操作 | 「営業終了時、レジの理論残高が自動計算されます。実際に数えた金額とズレがあれば理由入力を求められる仕組みで、レジの締め忘れ・不正防止に繋がります」 |
| 10:30-13:00 | タブD（本社）: ダッシュボードに切替 → 店舗ランキング・全店合計・アラートを見せる | 「本社は今デモした渋谷店だけでなく、全店舗を横断して見られます。売上が落ちている店舗には自動でアラートが立ちます」 |
| 13:00-15:00 | 質疑応答の時間として確保 | — |

### 見せ場
- KDSにQR注文が**手動更新なしで**流れる瞬間（Realtime）— 実際に画面を並べて「今スマホで押したものが、ここに一瞬で出ます」と言いながら見せると効果が高い
- レジ締めで差異が出た場合に「理由が必須」になる画面（不正・ヒューマンエラー対策として刺さりやすい）

### 想定質問と回答

| 質問 | 回答 |
|---|---|
| キッチンプリンターに直接印刷できるか | レシート・伝票印刷の抽象化基盤は実装済み（58/80mm、ブラウザ印刷は動作確認済み）。実機プリンター（Epson/Star）のSDK接続は導入店舗の機種確定後に実施する項目（基盤実装済み・接続待ち） |
| 複数人で同時に同じ画面を使っても大丈夫か | Realtimeで同期しているため、複数端末・複数スタッフが同じ画面を見ても状態がずれない設計。二重会計・二重予約もサーバー側で防止 |
| 本社が見れる情報を店長には見せたくない場合は | ロールベースの権限管理があり、本社/店長/一般スタッフ/アルバイトで見える機能・データ範囲が異なる。機能単位でのON/OFFも企業ごとに設定可能 |

## パターンC: 30分版 — +在庫/原価/勤怠給与/予算日報/SaaS管理

**ゴール**: 経営者だけでなく、店長・経理・労務担当まで含めた**全部署の業務が1つに繋がる**ことを見せる。
契約検討の最終判断者（経営者+バックオフィス責任者）向け。

### 事前準備
- 15分版のタブA〜Dに加えて
  5. 経理アカウント（`keiri@demo.tenpo.one`）ログイン済みタブ
  6. 運営コンソール（cypress管理者）ログイン済みタブ（機能フラグ・オンボーディングの説明用）
- 発注→入荷のデモ用に、在庫が少ない商品を1つ事前に確認しておく
- 給与計算のデモ用に、勤怠データがある期間（先月）を確認しておく

### 画面遷移手順

| 時間 | 操作 | 話すポイント |
|---|---|---|
| 0:00-15:00 | パターンBと同じ流れ | 同上 |
| 15:00-17:30 | タブA: 在庫 → 「移動」「発注提案」「予測」タブを見せる | 「発注点を下回った商品は自動でリストアップされます。曜日別の使用量から需要予測もできるので、経験と勘だけに頼らない発注ができます」 |
| 17:30-19:30 | 発注 → 新規発注 → 承認 → 入荷登録 | 「発注から入荷までの承認フローが記録に残ります。入荷すると仕入単価が加重平均で自動更新されます」 |
| 19:30-21:30 | 原価管理 → 商品のレシピ編集（食材+使用量） | 「レシピを登録すると、原価率・粗利益が商品単位で自動計算されます。原価計算をExcelでやっている店舗には特に刺さるポイントです」 |
| 21:30-24:00 | 勤怠・シフト → 打刻 → シフトの週グリッド・人件費vs予算 → 給与・歩合計算 | 「打刻データがそのまま給与計算のインプットになります。歩合ルールも設定でき、計算根拠が明細で日本語表示されます（税・社会保険は含まない試算である旨を明示）」 |
| 24:00-26:00 | タブD（本社）: 予算管理 → 日報（自動生成→承認） | 「予算に対する着地予測が自動で出ます。日報も現場で数字を打ち込む必要がなく、実績から自動生成→店長が一言コメントを添えて提出→本社が承認、という流れです」 |
| 26:00-28:00 | タブF（運営コンソール）: 機能フラグの説明 → 契約企業ごとにON/OFFできることを見せる | 「これは御社に合わせて機能を絞ったプランもご用意できる、という説明のための画面です（運営側の管理コンソール）」 |
| 28:00-30:00 | オンボーディング画面 → 導入時の初期設定ウィザードを見せる | 「導入初日は、会社情報→店舗→営業時間→テーブル→メニューという順にウィザードが案内するので、専門知識がなくても自社で設定を進められます」 |

### 見せ場
- レシピ編集で原価率がその場でリアルタイムに再計算される瞬間
- 給与明細の行を展開し、「時給×実働時間」「歩合の帯別内訳」が日本語で表示される瞬間（ブラックボックス化しない、が刺さる業種が多い）
- 日報の「自動生成」ボタン一発で数字が埋まる瞬間

### 想定質問と回答

| 質問 | 回答 |
|---|---|
| 会計freeeや給与King of Timeと連携できるか | 現時点ではCSVエクスポートで連携する運用（勤怠・給与・売上・経費すべて対応）。API連携は各社との契約・仕様確認後に追加実装する設計になっている（連携センター画面で状況を正直に表示） |
| 社会保険・所得税の計算は正確か | 現状は試算表示に限定しており、正式な社会保険料・所得税計算は対象外と画面上に明記している。導入時は税理士・社労士の確認を推奨（正確性を偽らない設計方針） |
| LINEでの予約・通知はできるか | 現状はシステム内の通知・呼出表示のみ。LINE公式アカウントとの連携は、必要な抽出条件（セグメント配信）はすでに実装済みで、契約後にAPI接続を追加する想定 |
| 他社に比べて何が強みか | 予約・POS・顧客・在庫・勤怠・給与・経営数値が別々のツールではなく、最初から1つのデータベースの上に設計されている点。後付けの連携ではなく、会計時にポイント付与・在庫減算・顧客更新・売上計上が単一の処理として同時に行われる |
| セキュリティは大丈夫か | 企業・店舗単位のデータ分離（RLS）をデータベース層で強制しており、URLを直接叩いても他社データにはアクセスできない設計。全操作は監査ログに記録される |

## 共通の注意事項

- 実機（プリンター/カードリーダー）・実際のStripe決済・freee等の外部連携は**「基盤実装済み・接続待ち」**と正直に伝える。ハッタリで「もう繋がっています」と言わないこと（`docs/external-blockers.md`に対応状況を一覧化済み、必要であれば商談後に共有可）
- デモ中に変更した設定（機能フラグOFF、負在庫許可等）は**必ずデモ終了後に元へ戻す**
- 質問が想定回答リストにない場合は、その場で断定せず「持ち帰って確認します」と回答する
