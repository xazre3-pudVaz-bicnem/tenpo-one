# v0.4.2 TRANSACTION & ACCOUNTING CONSISTENCY 完了報告

目的: v0.4.1で記録した「コードだけで解決可能な不整合・エッジケース」を潰し、
返金を含むすべての取引が **POS → 帳簿 → P/L まで1円もズレずにつながる** 状態にする。

---

## 1. 返金仕様（migration 00025/00026・refund_order v3）

### 正式定義（lib/metrics.ts — shared metrics layer）

| 指標 | 定義 |
|---|---|
| gross_sales（総売上） | 会計成立注文（paid+refunded）の total 合計。返金は控除しない |
| discounts（値引） | 同注文の discount_total 合計（総売上は値引後金額） |
| refunds（返金） | refunds.amount 合計。**返金の営業日**で計上（元売上の日ではない） |
| net_sales（純売上） | gross_sales − refunds |
| 会計件数・客数 | 会計成立注文（paid+refunded）基準 |
| 客単価 | net_sales ÷ 客数 |
| payment_total | payments（completed）合計。返金は refunds 側で別掲 |

ダッシュボード・売上レポート・予算・日報・レジ締め・CSV・顧客LTVの全画面がこの層
（`computeSalesMetrics` / `SETTLED_ORDER_STATUSES` / `expectedCash` / `computeCostVariance`）を使い、
**画面ごとに別の式を書かない**。service_charge / tips は将来項目（現行スキーマに無し・定義のみ将来拡張）。

### 部分返金
- 売上¥10,000 → 部分返金¥3,000 → 純売上¥7,000 が全画面へ反映（Playwright CASE1 / verify CASE1で実証）。
- **元取引は上書きしない**: orders.total は¥10,000のまま（gross保持）、orders.status も全額返金までpaid。
- 返金可能額 = 支払済み − 返金済み。超過は DB RPC が `REFUND_EXCEEDS_PAID` で拒否。
  注文行の FOR UPDATE により**同時実行でも合計が上限を超えない**（Promise.allSettled レース検証済み）。
- 二重返金: refunds は不変（`REFUND_IMMUTABLE`: UPDATE/DELETE禁止。journal_entry_id後付けのみ許可）。

### 商品単位返金（refund_items）
- 明細×数量×金額を指定（唐揚げ×2のうち1個 等）。値引後は line_total ベース単価で按分。
- 数量・金額とも元明細の未返金残を超えると `REFUND_ITEM_QTY_EXCEEDED` / `REFUND_ITEM_AMOUNT_EXCEEDED`。
- 明細合計 ≠ 返金総額は `REFUND_ITEMS_AMOUNT_MISMATCH`。UNIQUE(refund_id, order_item_id)。

### 返金と在庫
- 明細ごとに「在庫に戻す」を選択（既定OFF。返品あり→戻す / 提供済み→戻さない）。
- 戻す場合は finalize_order の減算2経路（①menu_item直結在庫・②レシピ）を**両方**鏡写しに
  `stock_movements 'return'` で記録し在庫加算。二重戻しは構造上不可（返金作成時に1回のみ実行）。
- **検証で発見・修正したバグ**: 00025は②レシピ経路のみ鏡写しで、①直接リンク（生ビール等の
  ドリンク在庫）が戻らなかった → migration 00026 で修正、実環境+Playwrightで実証。

### VOID と REFUND の分離
- refunds.kind: `void`=取引取消（**残額全額のみ**・`VOID_MUST_BE_FULL`）/ `refund`=成立済み取引への返金。
- 画面（注文詳細・履歴バッジ）・レジ締め・仕訳摘要（「うち取消N件」）・metrics（voidAmount分離集計）で区別。

### ポイント・クーポン整合
- 付与済みポイントは返金比率で比例取消（revoke）・ポイント払い分は比例返還（refund_return）。
  商品単位返金経由でも同一ロジックが働くことを実証。クーポン利用取引の返金も売上計算を壊さない
  （値引後グロスからの返金控除）。顧客LTV（total_spent）はDB側で返金時に減算＝常に純額。

## 2. 返金の仕訳（自動仕訳 第6ソース）

```
元売上仕訳: 借方 現金100/売掛金130       貸方 売上高400/401   (source_type=pos_sales)
返金仕訳  : 借方 売上高400/401           貸方 現金100/売掛金130 (source_type=pos_refund)
```
- 店舗×**返金営業日**で集計・source_id=`{storeId}:{date}` で冪等（2回確定しても1仕訳）。
- 税区分按分は元注文の order_items 8%/10% 比率（売上仕訳と同一手法・端数は合計一致保証）。
- payment ⇔ refund ⇔ journal_entry の相互リンク: refunds.journal_entry_id バックリンク+
  仕訳一覧の source絞り込み・注文詳細からの導線。

## 3. レジ締め（daily_closings 再設計）

```
理論現金 = 開始現金 + 現金売上 + その他現金入金 − 現金返金 − 小口現金出金
```
- クレジット/QR/電子マネー返金は現金残高へ**影響しない**（現金台帳は method='cash' のみ記帳）。
- 締め時snapshot保存: 総売上(gross)・返金・**純売上**・支払方法別内訳（売上/返金を別jsonb）・
  小口入出金・理論現金・実現金・差異（daily_closings 新6列）。
- **過去締めの不変**: 締め後の返金は返金発生日の営業日側へ計上され、既存 daily_closings 行は
  変わらない（verify CASE9で実証）。旧データ（新列未記録）は「—」表示で0円と断定しない。
- 30日売上推移は daily_closings.net_sales 参照（旧行はgross−refundへフォールバック）。

## 4. 原価の正式定義（理論と実際を混同しない）

| | 定義 |
|---|---|
| 理論原価 | 販売商品 × レシピ × 平均仕入単価（stock_movements 'sale' 相当の理論消費） |
| 実原価 | 理論原価 + 廃棄額（waste） + 棚卸差異額（count_adjust・不足=正） + その他調整 |

- `/app/reports` に**原価差異分析**カード: 理論原価 / 実原価 / 差異 / 差異率 + 内訳
  （廃棄・棚卸差異・その他）→ 在庫・棚卸へドリルダウン。
- P/Lカスケード・原価率・粗利率のラベルに「理論」を明示（`computeCostVariance`）。

## 5. P/L整合性

POS → Net Sales → 返金仕訳（pos_refund） → 試算表 → P/L が一致:
- 仕訳ベースの売上高posted集計が返金分だけ減り、metrics層のnet_salesと一致（verify CASE11/13）。
- 同一期間・店舗条件でダッシュボード / 売上レポート / 予算 / P/L の純売上が同一
  （全画面が同一クエリ条件+同一関数を使う構造で保証）。

## 6. 日報・営業日境界

- 日報: 総売上 / 値引 / 返金 / 純売上 / 客数 / 客単価（分母=純売上÷客数を注記）。
  旧日報スナップショットはフォールバック表示（勝手に再計算しない）。
- 営業日境界: 返金の business_date は `app_business_date(store)`（深夜営業カットオフ対応）。
  売上・会計・返金・レジ締め・日報が同じ営業日へ属する（open_register_session も同関数）。

## 7. 会計同時実行（再テスト）

- 同一注文の同時会計: payments 1件のみ（既存・再GREEN）。
- 同一注文の**同時部分返金**: FOR UPDATE 直列化により合計が返金可能額を超えない（新規実証）。

## 8. 月次締めとの整合

- 締め済み月への新規仕訳・修正・取消は `PERIOD_CLOSED` で拒否（既存）。
- 返金は返金日の営業日=通常は開いている当月へ計上されるため締めを壊さない。
  過去月の訂正が必要な場合は「管理者による締め解除（理由必須・audit）→修正→再締め」フロー（v0.4.1）。

## 12. 残課題

1. 支払方法別「純額」内訳: 返金のmethodと元支払のmethodが異なる場合（現金売上→カード返金等）、
   方法別の純額は近似になる（現在は売上内訳と返金内訳を別掲することで正確性を維持）
2. 複数レジ店舗の daily_closings が最終レジのexpected/counted/差異で上書き（v0.3からの既知課題・raw register_sessionsは保持）
3. 実原価の「仕入価格変動」内訳は未分離（現在は廃棄・棚卸差異・その他の3分類。加重平均単価の期間比較が必要）
4. 過去営業日を指定した遡及返金の入力（現在は常に当営業日計上。会計上はこれが正だが、運用要望があれば管理者限定の日付指定を検討）
5. guest_count 既定1名（テイクアウト/QR）による客単価の歪み（v0.4.1から継続）

```

    │
    ▼ 自動仕訳（冪等 source_type+source_id）

 └────────────────────────────────────────────────┘
    │ post_journal_entry（借方=貸方をDB強制・確定後不変・物理削除不可）
    ▼
```

**1円もズレない根拠**: (a) 全画面が同一のmetrics層・同一クエリ条件、(b) 仕訳は業務データから
冪等生成され借方=貸方をDBが強制、(c) 確定データ（payments/refunds/posted仕訳/approved給与/締め済み月）
は改変・削除がDB層で禁止、(d) 返金は返金営業日へ計上され過去のsnapshotを書き換えない。
